## MAP PROTOCOL
How and when the Excalidraw project map gets redrawn. Written so any session reproduces
the same map from this file, with or without the previous drawing's checkpoint.

**When:** when the MAP STATUS counter above reaches 3. A "shipped session" is one that
delivers a feature, pack, or fix set (doc-only passes do not count). Reconcile this file
FIRST, then draw the map from the reconciled file, then reset MAP STATUS. Never draw from
memory of a previous map.

**Zone-to-heading mapping (fixed):**
| Zone | Title on map | Source heading |
|---|---|---|
| 1 | SHIPPED — FOUNDATION | ## SHIPPED — FOUNDATION |
| 2 | SHIPPED — GAME PACKS | ## SHIPPED — GAME PACKS |
| 3 | NEXT UP (queued) | ## NEXT UP (queued) |
| 4 | FEATURES TO ADD | ## FEATURES TO ADD |
| 5 | BUG FIXES | ## BUGS |
| 6 | IDEAS — NOT SOLIDIFIED | ## IDEAS (not solidified) |

Every ZONE maps to a heading; not every heading is a zone. DEFERRED, STANDING RULES,
ADDING A PACK, CASINO GROUP, DECISION LOG and OPEN DECISIONS are reference sections that
are deliberately not drawn — they are reading material for a session, not scope. Adding
another reference section does not change the map; adding or renaming one of the SIX
above does, and must update this table in the same commit.

**Layout (fixed, so redraws are stable):** 3 columns x 2 rows. Columns at x=40, 560, 1080,
each 480 wide. Row 1 at y=95 (height 1120), row 2 at y=1240 (height 660). Zone header text
15px below zone top, fontSize 22. Items 440 wide, 40 tall, 46px step, first item 50px below
zone top; give a taller box (52-70) to any item whose label wraps past one line. Row 1 grew
from 540 to 730 on 2026-07-27 (SHIPPED FOUNDATION reached 14 items and overflowed its
zone), from 730 to 800 on 2026-07-28, when the completed pre-pack cleanup item grew
to a three-line box and left only 10px of slack, from 800 to 860 on the third 07-28
pass, when the two newly rendered shipped sessions needed exactly the 92px of slack zone 1
had left, from 860 to 920 on 2026-07-29, when zone 1's remaining 42px was 4px short of
the 46px one more item costs, from 920 to 990 on 2026-07-30, when zone 2 took three
multi-line casino items in one pass, and from 990 to 1120 on 2026-08-02, when zone 2 took
declarative modifiers and Casino Run. Each time it was raised pre-emptively rather than
waiting for the next entry to overflow it, since the fix is mechanical and the trap would
have landed on whoever added the next line.
ROW 2 GREW FOR THE FIRST TIME on 2026-08-02, 530 to 660: it had been a fixed height through
six passes because only row 1 was filling up, and zone 5 overflowed it by 20px once the
open bugs were all rendered. Both row-2 zones were raised together for the same reason row
1's are.
When a zone outgrows its height again, raise BOTH zones in its row together, and if it is
row 1, push row 2 down by the same amount so the columns stay aligned.

**Colors:** zones 1-2 green (#d3f9d8 zone / #b2f2bb items / #15803d header). Zone 3 yellow
(#fff3bf / #ffd8a8 / #b45309); the first three items get strokeWidth 2 and a leading number,
they are the committed next sessions. Zone 4 blue (#dbe4ff / #a5d8ff / #2563eb). Zone 5 red
(#ffc9c9 zone / #b91c1c header): OPEN bugs #ffc9c9, the chosen FIX #ffd8a8, "Watch" traps
#fff3bf, FIXED items #b2f2bb. Zone 6 purple (#e5dbff / #d0bfff / #6d28d9). Newly shipped
items in zones 1-2 get #c3fae8 + "(NEW)" until the next redraw.

**Cameras:** open 600x450 on the title, then 800x600 per zone in reading order (1-6), close
on a panorama covering the full canvas (1600x1950 at the current zone heights). Title fontSize 30 at y=15, subtitle 18 at y=56 with the month/year.

**Reconcile step (do this before drawing):** move finished items from NEXT UP into the right
SHIPPED section with a one-line summary and date; renumber the top three of NEXT UP; move
fixed bugs to FIXED in BUGS and drop anything stale; add anything new discussed since the
last pass; then draw.

**Committed file copy (always, added 2026-07-19):** the live MCP canvas does not render in
Claude Code sessions (unlike regular Claude chats), so the map must ALSO always exist as
`project-map.excalidraw` at the repo root — open it at excalidraw.com. It is generated, not
hand-drawn: `scripts/generate-project-map.mjs` holds the zone/item data and emits the file
with this protocol's layout and colors. On every redraw: update the item data in that script
to match the reconciled headings, run `node scripts/generate-project-map.mjs`, and commit the
regenerated file in the same commit as the reconcile. If the MCP canvas is unavailable in a
session, regenerating the committed file alone still counts as the redraw.

- [x] CASINO RUN, the co-op pack (2026-07-30). The crew shares ONE bank and plays a sequence of STAGES; each stage has a QUOTA the bank must reach and a budget of LEGS to reach it in, with a FLOOR underneath the whole run. Clear the last stage and everybody wins; drop through the floor and everybody loses. NAMING: the backlog used "floor" for the bank minimum, so the levels are STAGES and the floor is only ever the bust threshold — the two words never trade places, in the code or the UI. ITS OWN ENGINE, `packages/shared/src/casinorun.ts`, explicitly not `settleCash`: that engine is built on per-player nets summing to zero against a banker, and a co-op run inverts the assumption. EVERYTHING IS DERIVED FROM THE LEG LOG — bank, stage, attempt, status, clears, peak, comeback — the same call craps made for hands and Smashdown for its burn board, which is what makes undo a pop-and-re-derive rather than a pile of counters to unwind. THE HOST SETS A LUMP-SUM BANK; players do not buy in, and there is no per-player buy-in or cash-out field anywhere in the pack. QUOTAS ARE PRESET LADDERS, one choice at setup producing the whole curve, as `startingBank * (1 + escalation)^N` — the quota is the bank's TOTAL, not a delta. **THE LADDERS ARE SIMULATED, NOT FELT, and the first draft was badly wrong.** Proposed +15/+25/+40/+60% cleared 37/28/10/4% against the brief's own model, so the "casual" ladder would have lost the bank two nights in three. SHIPPED LADDERS, all mid-band and strictly ordered: **Casual +6% x4 stages = 75.5%, Standard +15% x4 = 52.8%, High roller +30% x5 = 22.8%, Degenerate +50% x5 = 10.5%**, at 20,000 seeded runs each. A MISSED STAGE DOES NOT END A RUN: it costs the attempt and forces a bane, so only the floor and the final quota end anything, which is what makes the modifier pile-up the pressure rather than a timer. Per-leg attribution rides along in meta as `myLegs`/`myDelta`. OFF-APP LEGS are free text, so a crew playing something the app has never heard of can still run one. TV: the bank at 19vmin and nothing competing with it, the quota and distance under it, the stage ladder, the house rules and whose leg was last at what. STATS: clear rate, deepest run, busts, biggest comeback as a named crew record, stages lost to the house, and clear rate per house rule behind "More stats" — crew-wide here, the mirror image of the cash packs' per-player rule, because a co-op result is the table's and identical for everyone on it. A seven-out is NOT a roll, so "rolls survived before sevening out" means what it says and an instant seven-out is a hand of zero. HANDS ARE DERIVED FROM AN EVENT LOG, never maintained, which is the same call Smashdown's burn board made for the same reason: undo of a seven-out has to REOPEN the closed hand AND hand the dice back, and doing that by unwinding counters is right until it isn't. Here undo pops one event and re-derives, so it is correct by construction; the shooter is read straight off the popped event. Handing the dice on voluntarily is logged as a `pass` and closes the hand too, so twelve rolls count as twelve rolls whether or not they ended in a seven-out. Rotation is by roster order over players still at the table, so a cash-out mid-session is skipped and a shooter who cashes out still passes to the next SEAT rather than to the top of the list — and the host can hand the dice anywhere, because the rotation is a default and not a rule. THE LIVE READ EXCLUDES THE OPEN HAND so the TV's "to beat" number is a real target; completion includes it, because the night ending means the hand happened. TV: the shared `MoneyBoard` grew a `hero` slot (an extension, not a fork) and craps fills it with the shooter, their live roll count, and the night's longest hand beside it. 29 new tests (183 -> 212) on the hands, the undo and the rotation. ## ADDING A PACK (the short checklist)
Most of what a pack needs is now derived from ONE registry entry. This lists what is not.

1. **Add the entry** to `SESSION_PACKS` in `packages/shared/src/packs.ts` (ledger key, gameName,
   keyPrefix, route, wsType, table, name, emoji, quickTitle). APPEND it; never insert above a pack
   that is already live, because `SESSION_PACK_KEYS` feeds the event TV's tiebreak and inserting
   would silently re-rank the live one. Everything data-driven follows from the entry, and the
   compiler finds the rest. Never change these five for an EXISTING pack: ledger, gameName and
   keyPrefix are written into the database and change nothing loudly — they just orphan history.
2. **Server:** the pack's own router, its state shape, its `materialize*` (the ledger unit is
   genuinely per-pack), and its `createPackRuntime({ ...packConfig("<key>"), extras })`.
3. **Mount it** in `apps/server/src/index.ts`. MANUAL ON PURPOSE: mount ORDER is load-bearing, so
   the public TV router goes with the other `/api/tv` mounts, above the authed routers.
4. **Client:** the pack page, its TV view, its CSS, and the format list in `apps/web/src/packs.ts`.
5. **Lazy routes** in `App.tsx`. MANUAL ON PURPOSE: Vite needs a static literal inside `import()`
   to split the chunk, so this cannot be looped. Add the chunk to `prefetch.ts` too — that one IS
   type-checked, so forgetting it fails the build rather than silently slowing a tap.
6. **Guest linking:** export `guestNames*` / `creditGuest*` and register them in `guest-link.ts`.
7. **Safe area:** nothing to do for the pack PAGE (index.css insets every shell structurally), but
   a TV screen that sets its own `padding` must fold `env(safe-area-inset-*)` into its own
   `calc()`, because a class rule beats the zero-specificity shell inset. Casino packs get this
   free from `casino.css`.
8. **A CASINO pack is much less than the above.** See CASINO GROUP: the engine, the money routes
   and every money screen are shared, so steps 2 and 4 shrink to a handful of callbacks and some
   copy.

## CASINO GROUP (design, shared by the four CASH packs)
Written down on 2026-07-29 with the blackjack session so roulette, craps and poker do not have
to rediscover any of it. Blackjack is SHIPPED and is the worked example — read its files
alongside this. Everything below is already built and tested unless it says otherwise.

**Four packs, not one.** Blackjack, roulette, craps, poker, each with its own registry entry and
its own `ledger` key, so each shows as its own leaderboard tab. That is the point: a blackjack
net and a poker net are different skills, and collapsing them would be exactly what the pack
registry's own warning about `gameName` says never to do. They share ONE engine, so each pack
file stays thin. Build order is blackjack -> roulette -> craps -> poker, with poker last because
it carries a second, placement-based `tournament` format on top of the net-based one.

**The engine: `packages/shared/src/cashgame.ts`.** Pure, dependency-free, fully unit tested
(`packages/shared/tests/cashgame.test.ts`). It owns buy-in, rebuys, cash-out and net per player;
net as `cashOut - (buyIn + sum(rebuys))`; placement derived by ranking net descending with ties
as co-placements at competition ranking (two at 1, next at 3, the Smashdown convention); the
zero-sum balance check; and `summarizeCash` / `CashSummary<D>`, where D is the pack's own
per-player detail and is the ONLY thing that differs between packs.

**Three shared layers, added in this order for a reason.** The ENGINE landed with blackjack. The
SCREENS (`apps/web/src/casino/`: CasinoSetup, CasinoTable, MoneyBoard, money.tsx, casino.css) and
the SERVER ROUTES (`apps/server/src/casino-runtime.ts`) landed with roulette, once there were two
real examples to generalise from rather than one to guess from. What that leaves a new pack is:
a registry entry, a server file supplying four callbacks (`newState`, `summarize`, `ledgerMeta`,
`applyDetail`) plus its own tracker routes, a page supplying copy and its cash-out fields, and a
TV handing `MoneyBoard` a brand and a per-player subline. `packages/shared/src/roulette.ts` and
`apps/server/src/roulette.ts` are the template — read them, not blackjack's, since blackjack
carries a little extra history.

**MONEY IS INTEGER CENTS. EVERYWHERE.** Never a float, never a JS number holding dollars. This is
not tidiness. Floats drift by fractions of a cent, so the balance check below would fail on
sessions that are perfectly correct, which is a miserable bug to chase months later. Store cents
in the session jsonb, in `match_participants.meta` and on the wire; format at the EDGE only, with
`formatCents` / `formatCentsSigned` out and `parseCents` in. The server's `cents()` helper rejects
a non-integer outright rather than rounding it, because rounding would hide a client that had
started doing dollar arithmetic. There is a named float-canary test; do not delete it.

**Placement is derived, so the ledger does not change.** These packs feed the existing
`matches` / `match_participants` tables with NO schema change and NO change to `stats.ts` at all.
That is why this shape was chosen. **Do not add columns to the ledger for money.**

**Who banks, per session.** Session state carries `bank: "player" | "casino"`, chosen by the host
at start.
- `bank: "player"` — a crew member is the house. Their net is DERIVED as the inverse of every
  other player's and is NEVER typed in, so the table sums to zero by construction. The banker's
  own buy-in (their float) and cash-out (what came back) ARE recorded, and the balance check
  compares their count against what the players' numbers say it should be. If it disagrees, show
  "the table does not balance, off by X" rather than silently materializing bad numbers. It is a
  warning, not a veto — the host confirms and it records. The check is SKIPPED, not failed, until
  the banker has cashed out. No other pack in the app can check its own correctness like this.
- `bank: "casino"` — a real casino is the house. Nets are independent, no derived player, no
  balance check, and the table correctly does NOT sum to zero: the missing money went to a
  building.

**Materialization unit is the SESSION, not the hand.** One `matches` row per completed session,
one `match_participants` row per player, placement from net rank. Buy-in, rebuy count, cash-out,
net, session length and the pack's detail stats ride in `match_participants.meta`. `character`
stays null for every casino pack. `matches.format` is `"cash"` for all four. Standing rule 5
applies unchanged: guests are skipped until linked.

**Live tracker: built for every pack, defaults OFF.** Each pack ships two input paths. (1) The
DEFAULT is the cash-out screen: two interactions per player per night, a buy-in at the start and
a short cash-out form at the end. That is the minimal-input path and the one most nights use.
(2) The OPT-IN is a live tracker the host can flip on mid-session, feeding the per-pack detail
stats. THE RULE: the tracker being off must never lose a stat the cash-out form could capture.
Anything the tracker produces is either ALSO a typed box on the cash-out form (prefilled from the
tracker when it ran, and typed beats derived per FIELD, not per player) or is genuinely
un-reconstructable — a roulette streak, a craps roll length — and simply absent when it was off.

**Free stats, from buy-in and cash-out alone. Do not add input to get these.** Lifetime net per
pack and overall, win rate as percent of sessions finishing up, biggest night up and down,
average buy-in, average net, rebuy rate, current and longest winning-session streak, ROI as net
over total buy-in, net per hour from session timestamps, best and worst night. Blackjack's
`/api/groups/:id/blackjack-stats` computes all of them; copy it.

**Per-pack detail stats** (recorded here so nobody redesigns them):
- Blackjack (SHIPPED): biggest bet, biggest win, blackjacks hit.
- Roulette (SHIPPED): max consecutive winning spins (REQUIRES the tracker, no box to type it
  into), favourite bet type.
- Craps (SHIPPED): longest roll (rolls survived before sevening out) and points made, both
  typed-or-derived; biggest bet and biggest win typed-only, since its tracker follows the dice.
  Longest roll is also a CREW-WIDE record on the stats panel, not just a personal stat.
- Poker: biggest pot, bad-beat note, plus a second `tournament` format that is placement-based
  rather than net-based.

**A pack's own headline on the TV goes in `MoneyBoard`'s `hero` slot**, not in a forked board.
Craps put the shooter there (name, live roll count, the night's longest hand to beat) and the
slot is generic: poker's pot and the co-op quota are the next two things that want it.

**STAKES (SHIPPED).** Session state carries `stakes: "real" | "play"`, chosen on a dropdown at
start and fixed for the night. Absent means real, which is every night recorded before it
shipped. WINS AND PLACEMENTS UNIFY across stakes; ONLY MONEY SPLITS — nights, win rate, streaks,
rebuys and hours count once, while net/staked/averages/ROI/best/worst/net-per-hour are computed
per stakes and printed on their own line. There is no combined net on the aggregate at all, so
nothing can render one. Format through `money(stakes)` from cashgame.ts, never `formatCents`
bare, inside any casino screen: the bound helper is what stops a missed call site showing
dollars on a play table, and the browser suite checks that invariant directly. Two signals mark
play money — the `P$` prefix and the violet badge — and up/down stay green/red, because those
mean direction rather than currency. Copy says "play money", never Monopoly.

**CASINO RUN is in this group but NOT on this engine** (2026-07-30). It shares the money
primitives, the modifier deck and the `--cg-*` tokens, and nothing else: one shared bank
against a target instead of per-player nets, so it has its own state module, its own routes
and its own screens. Everything below describes the four CASH packs. See SHIPPED.

**MODIFIERS are shipped and shared** (2026-07-30). `packages/shared/src/modifiers.ts` owns the
24-card deck and the draw; `casino/modifiers.tsx` owns all three renderings (the setup picker, the
strip on the pack page, the wall on the TV). A pack gets every one of them by passing its LEDGER
key to `CasinoSetup` — there is nothing per-pack to write, and a new casino pack that adds no
cards of its own still has the twelve "any" cards in its pool on day one. The rule that does not
move: the app displays and records, it never computes. See DECISION LOG.

**TV is a live money board**, and it IS a shared component now (`casino/MoneyBoard.tsx`, extracted
with roulette). Who is up, who is down, rebuy counts, running totals, sorted by net, updating over
the WebSocket on every buy-in, rebuy and cash-out. A pack passes a brand, an optional header
extra, and a per-player subline tail; everything else is the same board, so two packs can never
disagree about who is up.

**A casino pack's stylesheet is a token block, not a stylesheet.** All structure lives in
`casino/casino.css` and reads `--cg-*` tokens with `--gn-*` fallbacks. A pack sets the backdrop,
the brand glow and about eight token values on its `.xx-root` / `.xx-tv` — roughly twenty lines.
DO give each pack a distinct accent: two money boards that look alike are genuinely confusing
across a room, so blackjack is gold on oxblood and roulette is teal on green felt.

**Per-player buy-ins.** The setup screen carries an amount per seat as well as a table default,
because the banker's float is nearly always different from everyone else's. A seat FOLLOWS the
default until it is touched, so changing the default still moves everyone who has not been given
their own number. Only overridden seats are sent (`buyIns`, keyed by roster index).

**Deferred, do not build:** cross-pack night net. See FEATURES TO ADD.

## DECISION LOG
- A deck rated by FEEL is wrong about half the time (2026-08-02): the playtest re-rated 21 of 36 cards, and the errors were not small — a severity 1 that ended runs outright, severity 3s that did nothing. Severity drives the draw weighting AND Casino Run's escalation, so a mis-rated deck makes the "gentle at first, nasty later" curve a lie. Ratings are now measured and bucketed by a test. The model is approximate and says so; what it buys is the ORDERING, which is what severity is for.
- CO-OP AND TEAMMATE RESULTS ARE A DISTINCT RIVALRY OUTCOME, NOT A TIE, and `side` is the primitive (2026-08-02, James's call). Casino Run writes an identical participant row for everyone on a run, so the placement comparison in `buildRivalry` scored a shared run as a DRAW between every pair of players in it. THE CHEAP FIX WAS REJECTED ON THE SPOT: skipping `format = "casino_run"` the way `isSeriesSummary` is skipped works today and is wrong the moment doubles ping pong, beer pong, cornhole or foosball land, because the same two people are teammates in one match and opponents in the next. Team structure cannot be a property of the PACK; it has to be a property of the MATCH. So `match_participants` gained a nullable `side text`. NULL MEANS NO TEAM STRUCTURE: every row written before the column existed and every free-for-all result forever, and null rows classify EXACTLY as they did before, which a brute-force test over every placement/isWinner pair asserts. A non-null string names the side; two players sharing a non-null value were teammates, different non-null values are opponents. The value is opaque and only ever compared for equality. `buildRivalry` gained a fourth outcome, `together`, checked AHEAD of win/loss/tie (it has to be, because the identical rows would otherwise reach the comparison and tie), counted separately in the totals and in the per-game breakdown, and SKIPPED by the meeting streak: counting it as a win would read a co-op night as an unbeaten run, and breaking the streak would claim something happened between two people who were not playing each other. BUILT AT CASINO RUN TIME ON PURPOSE, with Casino Run as the only writer this session, so the doubles formats already in IDEAS have the primitive waiting rather than having to invent it under deadline. Deploy: `ALTER TABLE match_participants ADD COLUMN IF NOT EXISTS side text;`
- In a game where the bank must GROW, raising the minimum bet is a boon (2026-08-02): three cards were labelled banes for forcing bigger bets, which is help, not harm — bold play is optimal against a target. Two were given a real cost (the bank posts the ante dead once a leg); the third was relabelled. A wrong SIGN on a card is worse than a weak card: it is a lie on the screen the table is reading. The direction test now checks both betting styles, because checking bold play alone is exactly what missed it.
- Flat per-leg costs are lethal here, so money cards take a share (2026-08-02): a run must grow the bank ~75% over ~10-20 legs, so a card costing one ante a leg removes ~40% of the bank and ends the run on its own. That is why the rake and vig cards are shares of the pot or the win rather than multiples of the ante — and why a share of the win cannot be rendered as money, since the app never sees a hand.
- "Stake" is a banned word for anything except real-vs-play money (2026-08-02): `stakes` has meant that across the casino group since the flag shipped, and round three quietly introduced "the table stake" as the unit for bonus percentages. One word, two jobs, exactly as "floor" was doing before stages were named. The unit is now named per pack — the ANTE in a run, the BUY-IN at a cash table — and the card text prints it, so "10%" is never left as ten percent of something unstated.
- `appliesTo` has three cases, and the middle one earns its keep (2026-08-02): "any" (every table, co-op included), "cash" (needs per-player money, so never a co-op run), and a table list (that game, AND a run, because a run plays that game). Collapsing "cash" into the table list is what briefly put Mercy chip's free REBUY in front of a pack that has no buy-ins. "A run plays blackjack" and "a run has per-player money" are different claims and the type now says so.
- A run holds every table's cards, dormant until it plays that table (2026-08-02, James: "in casino run you might jump from roulette back to blackjack then to roulette"): the pack-specific half of the deck was unreachable in the only mode that plays all three games. Making the run's pool the union was the easy half; the useful half is saying WHEN each card bites, which is at the moment a game is picked for a leg, not on a tag nobody connects to anything.
- House rules are about the BOARD, not the room (2026-08-02, James: cards should be "more about the totals on the board and the money, not interaction like where the phone is or talking"). The first deck had six cards policing behaviour — no talking, phones off the table, last to sit antes. They are party rules wearing a casino costume: they never touch a number the app tracks, they are unenforceable without somebody appointing themselves referee, and one of them ("pays the table a forfeit") did not even name a cost. Retired and replaced with cards that move stakes and totals. RETIRED IDS ARE NEVER REUSED, asserted in a test: a run played under one still has rows in the ledger, and reusing the string would silently merge two different cards' histories.
- A card that mentions money must name a fraction, and the app renders it (2026-08-02): "pays a bonus" is an argument waiting to happen at a table with drinks on it. `bonusPct` plus `modifierRule()` turns it into a real figure against the table's own stake. This does NOT cross the line the group holds — the app is doing arithmetic on a number the table declared, exactly as it does for the minimum ante, not deciding whether a hand won. - Severity pips needed a legend or they were decoration (2026-08-02): three dots with no key anywhere is a picture of a number nobody can read. Worth logging because it is the second time a "self-evident" visual in this pack turned out not to be.
- A co-op run has to be LOSABLE, and the first cut was not (2026-08-01, James: "there appears to be no way to lose, it just keeps giving more attempts which seems like no fun"). He was right, and the simulation put a number on it: a table betting the minimum took ~1,100 legs to resolve and half a percent of runs never resolved at all. The original rule — a missed stage costs the attempt and nothing else — made the leg budget decorative and left the floor as the only fail state, which a hovering bank dodges forever. `attemptsPerStage` is the fix, and the reason it is the RIGHT fix rather than just a harder one is that it is aimed: it takes a grinder from 1,100 legs to 15 while moving bold play by under a point, so it ends the behaviour that was un-fun without changing what a committed table experiences. The ante rising on every miss is the same pressure applied gently — grinding gets more expensive before it gets fatal.
- Tracking a minimum ante is bookkeeping, not refereeing (2026-08-01): worth stating because it sits close to the line the whole casino group holds. The app never computes whether a bet WON — that is the humans' job and it does not change. What it can do is keep a number the table already agreed on and apply the rises the cards call for, which is the same kind of work as counting legs or stages. If a future session wants the app to compute what a modifier PAYS, that is the line, and it is still where it was.
- One-shot tokens live in the leg log (2026-08-01): a purchase is an entry that moved the bank, so undo pops it and everything — the refund, the un-holding of the card, the ante relief it cancelled — falls out of the same re-derivation that already existed. Buys are marked `kind: "buy"` and absent means "leg", so no migration was needed. Deliberately NOT blocked on affordability: spending the last of the bank on a hedge is a legitimate and in-genre way to end a run, and the floor check catches it like anything else.
- Casino Run is play money, full stop (2026-08-01, James's call): the quotas climb to multiples of the starting bank and the hardest ladder is designed to be unwinnable, so a real-money option would be offering people a losing proposition by design. - The modifier deck is 50/50 by assertion, not by intention (2026-08-01): it shipped 11 boons to 13 banes, and the "any" pool — the ONLY pool Casino Run draws from — was 4 to 8. - Modifiers are DECLARED, never enforced (2026-07-30, James's brief, restated here because it is the line a future session will try to cross): the app shows a modifier's rule and records that it was live; it never applies its effect. The trade as it stands: one tap at setup buys the rule on the TV all night and win rate per card for free. - A modifier `id` is permanent, everything else about a card is not (2026-07-30): ids go into `match_participants.meta`, so renaming one does not error — it orphans that card's entire history and the stat simply vanishes from the panel. Writing them to every participant is redundant across a session's rows and that redundancy is the point — it needs no schema change and answers the question directly. - Per-modifier money is PER PLAYER, and the panel admits it is correlation (2026-07-30): a crew-wide net per modifier reads as zero on every player-banked night, because the table is zero-sum by construction — that is what the balance check enforces. So the only honest grain for money is one person's own nights. And since the app never applies a modifier, the panel cannot claim a card caused anything; it reports how the nights carrying it went, and says so in its own copy. - The draw takes a deck, a count, a filter and a weighting (2026-07-30): `drawModifiers` could have been `drawTwoForSetup()`, which is all this session needed. - Co-op is CASINO RUN, its own pack, not a format inside the existing ones (2026-07-30, James's design): the earlier backlog entry described co-op as a mode you could switch a blackjack table into. Serving both from one engine means a branch through every function that four packs depend on, in service of the one caller that disagrees with it. As its own pack it reuses what it genuinely shares (integer cents, the money inputs, the `--cg-*` tokens, the modifier deck) and owns its own settlement. THE COST IS REAL AND ACCEPTED: a co-op leg played at blackjack lands under Casino Run, not Blackjack, so it does not appear in blackjack's lifetime money. That is the right trade — the alternative is co-op rows polluting a per-player net stat they do not obey — but it is a loss, and the pack's own copy should say so rather than leaving people to discover it.
- Wins unify across stakes, only money splits (2026-07-30, James's call, and it REVERSES an earlier answer): the first instinct was to keep play money entirely separate — its own totals, its own record, its own everything — and that is wrong in a way that only shows up in use. A win is a win. You either finished the night up or you did not, and whether the chips were worth anything does not change what happened at the table, so splitting the win rate would quietly halve somebody's record the day the crew played a pretend night. What mixing genuinely corrupts is the TOTALS: adding a $60 real net to an 80-play-chip one produces a confident number that is arithmetic nonsense. So the line is drawn exactly there. Nights, win rate, streaks, rebuys, hours and nights banked count once; net, staked, averages, ROI, best, worst and net-per-hour are computed twice from the same rows. The implementation detail that enforces it: the aggregate has NO combined net field at all, so a later screen cannot render one by accident — the only way to get a total is to ask for a stakes.
- One games row, no second leaderboard tab (2026-07-30): the tempting implementation of play money is a second `games` row per pack ("Blackjack (play)"), because then every existing reader splits for free. It was rejected, and the reason is that it would split the wrong thing. `games.name` is the JOIN KEY for the crew leaderboard tabs, so a second row means two tabs, two histories, two of every unified stat, and a player's Blackjack record silently becoming two records — which is precisely the outcome the registry's own warning about `gameName` exists to prevent, and precisely the opposite of "wins unify". Stakes therefore rides in `match_participants.meta` next to the money already there, `ensureGame` is untouched, `stats.ts` is untouched, and the split happens in the one place that should know about it: the pack's own stats panel. The cost is that the split is a read-layer concern rather than a free consequence of the schema, which is the right cost to pay.
- An absent stakes value means REAL, and that decision is load-bearing (2026-07-30): every ledger row written before this shipped carries no stakes, and every `formatCents` call site outside the casino passes no stakes. Both had to keep meaning dollars, so the parameter is optional everywhere and absent is real rather than "unknown". Defaulting the other way would have moved a crew's entire real-money history into play money overnight, silently, with no migration to notice. The server picks the same direction for the same reason: anything that is not literally the word "play" in a start body is real, because a malformed request recording a real night as pretend is the more damaging of the two mistakes. Both directions are named tests.
- Two signals for play money, and up/down keep their colours (2026-07-30): the brief asked for a distinct prefix plus a different colour token so the two can never be confused across a room. The prefix is `P$` — plain ASCII, so it survives a TV browser, a screenshot and the canvas recap card, where a currency glyph might not — and the colour is a violet badge on the pack page and the TV header. What was NOT done is tinting the money itself: green-up and red-down mean DIRECTION, not currency, and hijacking them for stakes would have traded one confusion for a worse one. The badge is the signal you catch without reading a number, which is the case the requirement was actually about; the prefix is the one that survives being photographed. The related implementation call is `money(stakes)`, a bound formatter each casino screen takes ONCE: threading a stakes argument through twenty individual call sites is exactly the kind of list this repo has been bitten by, and a missed one renders play money as dollars. The browser suite now asserts the invariant directly — on a play table, a `$` not preceded by a `P` is a bug — because no unit test can see a component that forgot to ask.
- Craps' hands are DERIVED from an event log, which is the only reason its undo is correct (2026-07-30): the session brief called undo "the easiest thing in the session to get subtly wrong", and it was right about why. Undoing a seven-out has to do two things at once — reopen the closed hand with everything it had, and hand the dice back to whoever sevened out — and the natural implementation keeps a roll counter plus a `shooterId` and unwinds both by hand. That is right until the day it isn't: undo twice across a shooter change, or undo a point instead of a roll, and the counter and the dice disagree with each other in a way nothing errors about. So the log is the truth and `crapsHands()` is the only thing that reads it, exactly as Smashdown's burn board is only ever written by `burnedFrom(games)`. Undo pops one event and the hand reopens on its own; the shooter comes straight off the popped event rather than being recomputed. The one piece of state carried alongside is `shooterId`, because after a seven-out the dice belong to somebody with no events yet — and even that is restored from the event rather than guessed. Two smaller calls fell out of the same model. A SEVEN-OUT IS NOT A ROLL, so "rolls survived before sevening out" means what it says and an instant seven-out is a hand of zero rather than one. And handing the dice on voluntarily is logged as a `pass` that CLOSES the hand, because twelve rolls are twelve rolls whether or not they ended badly, and a hand that never closed would otherwise vanish from the record.
- The live longest-hand number excludes the hand in progress; the ledger includes it (2026-07-30): the TV shows the current shooter's roll count next to "to beat", and if the open hand counted towards the record those two numbers would be the same the moment somebody took the lead — a target that is always exactly what you have already done is not a target. So live reads take closed hands only. At completion the night is over, which means the hand that was in progress is a hand that happened, so `crDetail(..., { includeOpen: true })` is what the ledger writes. Same shape as `settleCash({ final: true })` treating an absent cash-out as a bust only once the night ends, and for the same reason: "unknown" and "finished" are different states and the boundary between them is the moment the host taps End.
- Craps CAN type its longest roll and roulette cannot type its streak, and the difference is real (2026-07-30): the group rule says a stat is either reconstructable — so it gets a box on the cash-out form — or it is not, and then it is absent rather than invented. Roulette's winning streak got no box, deliberately, because nobody honestly remembers a run of spins. Craps' longest roll gets one, because a table ARGUES about how long somebody held the dice and remembers the answer; it is the one number in the pack everybody at it already knows. Applying the roulette precedent mechanically would have made the tracker mandatory for the pack's headline stat, which is the opposite of the minimal-input rule. The tell for future packs: ask whether the room would still know the number tomorrow, not whether the app could have computed it.
- Longest roll is a CREW record, not a personal stat (2026-07-30, James's call): every other detail stat in this group is per-player and sits on a player's own subline. Longest roll gets its own headline on the crew leaderboard naming who holds it, because that is how it works at a real table — the number people know is who has held the dice longest, full stop, and burying it inside one player's row would lose the thing that makes it worth tracking. Mechanically it is free: `cashLifetimeStats` already returns every row's meta bag, so the panel takes a max across all players with no new query and no new endpoint. `CasinoPanel` grew one optional `record` slot for it, which poker's biggest pot will probably want too.
- Picker grouping lives on the CLIENT list, not the pack registry (2026-07-30): the obvious place for a `group` field is `SESSION_PACKS`, and it is the wrong one. The related decision is the comment: `group` is marked DISPLAY ONLY in the type, because this repo has three fields that are permanent and silent when changed (ledger, gameName, keyPrefix) and somebody reading a fourth string field in a pack definition should not have to work out which kind it is. An empty group renders nothing, so the next pack joins a section by setting one field.
- Mario Party gave up the die (2026-07-30): 🎲 was Mario Party's emoji and craps has the stronger claim on it — a die IS craps, whereas Mario Party's own scoring unit is the star it now carries. Worth a line only because "never change a pack's identifiers" is a rule in this file, and this looks like breaking it: it is not. - The casino screens and money routes were extracted on the SECOND example, not the first (2026-07-29, the roulette session): blackjack shipped with its money board, setup screen, live table and every money route inline, and a note saying roulette would decide whether to extract them. Extracting on one example is guessing at what generalises; building roulette made the answer trivial to see, and it was not the answer a guess would have given. The board turned out to be identical LINE FOR LINE, with only a brand, a header clause and a per-player subline differing — three props — while the thing that looked most likely to be shared, the tracker, turned out to be the one genuinely per-pack piece (a blackjack hand is a bet and a result, a roulette spin is a bet type and won/lost, a craps roll is neither). - Sharing the casino ROUTES does not contradict "routes stay per-pack" (2026-07-29): pack-runtime.ts states plainly that each pack keeps its own routes and request validation, because "a shared validator would drift into a lowest common denominator". `casino-runtime.ts` shares routes anyway, and the distinction is real rather than a convenience. That earlier call was about Smash vs Mario Kart vs Ping Pong, whose bodies genuinely differ — a fighter pick, a race result, a game winner — and where a shared shape would have to be invented. The casino packs are a SUB-FAMILY with one data model, already shared and already tested: the body of a rebuy is `{ playerId }` in all four, not by coincidence but because they are all the same cash game with different games attached. Sharing there is sharing one idea, not flattening four. The line was still drawn: the tracker routes stay in each pack file, and they are the routes whose bodies actually differ. If a fifth casino-shaped pack ever wants a different money model, the honest move is to stop calling it a casino pack rather than to add a flag to this runtime.
- A per-player buy-in FOLLOWS the table default until it is touched (2026-07-29, James's request): the obvious implementation copies the default into each seat when the seat is added, and it is wrong in a way that only shows up in use. A host sets $20, adds four people, then decides the night is a $40 night — and with copied values, nothing moves, so they have to edit four boxes and will miss one. Tracking the override as `null` = "follow the default" makes the common case free and the deliberate case explicit, and it needs no extra UI: the seat says "on the default" or "their own $100" with a way back. The React detail worth keeping is that the input's `key` carries the current default while a seat is untouched, so changing the default remounts and re-seeds it, and becomes stable the moment the seat has its own number — the alternative, a controlled input reset by an effect, fights the user's half-typed text. The server side of this had ALREADY SHIPPED with blackjack (`buyIns`, keyed by roster index) and was reachable by nothing, which is its own small lesson: a validated endpoint with no screen is not a feature, and it sat there for a day looking like one.
- Roulette's two stats are different IN KIND, and that is the group rule made concrete (2026-07-29): favourite bet type is reconstructable — anyone can say "I was on red all night" — so it is a typed field on the cash-out form AND derived from the tracker, with typed winning. Max consecutive winning spins is NOT reconstructable, because a streak is an ordering fact and nobody remembers it honestly at 1am, so it requires the tracker, is null rather than zero when the tracker was off, and has DELIBERATELY NO BOX to type it into. That last part is the actual decision. Offering a field would have been friendlier and would have quietly filled the ledger with guesses, and a lifetime "best run" stat assembled from guesses is worse than one that admits it only knows the nights somebody was counting. A test asserts that a `bestStreak` smuggled into a typed detail bag is ignored on read, so a later well-meaning change cannot open the door by accident. Zero would have been the other tempting answer and is the worse lie: it claims the player never won twice in a row.
- The safe-area inset is structural now, because the hand-written list did exactly what hand-written lists here always do (2026-07-29, found by James on a phone within hours of the blackjack deploy): the iOS shell paints under the status bar by design (`viewport-fit=cover` plus a black-translucent status bar), and every root shell is supposed to inset its own CONTENT with `env(safe-area-inset-*)` while its background still bleeds edge to edge. That rule was applied by listing the shell class names, and blackjack shipped without `.bj-root` on the list, so the entire pack sat under the clock and its back button was unreachable. It is the same silent-registration shape as the `ping_pong` ledger typo and the `beerio` emoji key: self-consistent code, nothing to compile against, no error, and only findable by holding a real device. The fix could have been one more class name; it is `:where(#root) > *` instead, which is a precise description of "the shell" because every route renders exactly one element as #root's child, and which a new pack cannot fail to be covered by. The `:where()` is load-bearing and worth stating: an `#id` in the selector would outrank every class, so a plain `#root > *` would have SILENTLY REPLACED the padding on the five TV screens that set their own `calc()` insets — trading a bug on one pack for a subtler one on five. Zero specificity keeps this a floor that anything can override, which is what a default should be. The remaining hand-maintained half is deliberate: a screen that sets its own padding must fold the insets into its own calc(), and that IS forgettable — `.pp-tv` had never done it and was found by this sweep. It is a smaller surface (only TV screens do it) and it degrades to "a TV has slightly wrong padding" rather than "a phone's back button is unreachable", which is the right place to accept the risk.
- THE UNIT IS CURRENCY, and this SUPERSEDES the bragging-rights-only entries (2026-07-28, James's call; implemented 07-29 with blackjack). Two places in this file said the opposite and are now updated rather than left to contradict each other: the "Wager ledger" idea, which read "bragging rights only, never money", and the DEFERRED line "Money wagers: regulatory mess. Bragging rights only." The second is kept STRUCK THROUGH rather than deleted, because the reasoning it rested on is still the boundary and deleting it would lose that. THE DISTINCTION THAT MAKES THIS FINE, and it is the whole argument: the app RECORDS WHAT A HOME GAME ALREADY DID. It does not facilitate a wager, hold a balance, transfer anything, settle anyone up, or take a cut. A cash night's ledger row is a note of what happened, in the same way the recap card is a note of who won — the money moved between people at a table, in cash, with or without this app. Everything that would actually MOVE money (payments, escrow, settle-up transfers, a payout button) stays deferred on exactly the original grounds, and that line is worth holding: it is the difference between a scorekeeper and a payment processor, and it is much easier to hold now than after someone has asked for a Venmo button. Recording both halves because a superseded decision with no successor entry reads as an oversight three sessions later, and a superseding one with no statement of what still holds reads as a licence.
- RIVALRIES INCLUDE CASINO NIGHTS, casino-banked ones too, WITH the caveat stated (2026-07-28, James's call; implemented 07-29). Because placement is derived from net rank, a cash night produces ordinary `match_participants` rows and every existing reader picks them up for free — including the rivalry pages, which will now show two people as having "met" on a night they were both playing against the house rather than against each other. On a player-banked table that is defensible: the banker genuinely is the other side of every hand, and finishing above someone on the night is a real comparison. ON A CASINO-BANKED TABLE IT IS THE WEAKER CLAIM, and that is the caveat: the players were not strictly playing against each other at all, they were each playing the building, and their relative net is closer to a shared circumstance than to a head-to-head. James's call was to include it anyway rather than special-case it. Logged here with the caveat spelled out for one specific reason: if the rivalry pages later read oddly — someone's record against a friend swinging on nights they never competed — the reason is ON RECORD, and the fix is a one-line filter (skip rows whose `meta.bank === "casino"` in the rivalry MEETING map, which is already the one place head-to-head encounters are counted) rather than an investigation into where phantom meetings came from.
- Money is integer cents, and the balance check is why that is not a style preference (2026-07-29): every amount in the casino group — session jsonb, `match_participants.meta`, request bodies, the client's own state — is an integer number of cents, and dollars exist only at two edges. The reason is specific rather than general hygiene. The zero-sum check asks whether a table's nets sum to EXACTLY zero, and in binary floating point they routinely do not: 3.33 + 3.33 + 3.34 is 10.000000000000002, so a night that was entirely correct would have announced itself as off by two ten-billionths of a cent and sent the host hunting a mistake that did not exist. That is a miserable failure to debug months later, when the only evidence is a warning nobody can reproduce. So `parseCents` parses from the DIGITS rather than through `parseFloat` (exact by construction, not exact because `Math.round` usually rescues it), the server's `cents()` REJECTS a non-integer rather than rounding it (rounding would hide a client that had started doing dollar arithmetic, which is the exact regression this is guarding against), and there is a named canary test built from many small odd amounts summing to a round total that fails the moment anyone reintroduces a float. One small thing found while writing it: a table that comes out exactly even produces `-0` for the derived banker, which compares equal to zero everywhere but prints as "-0" on a TV, so it is normalised.
- The ledger unit is the SESSION, and that is what let the casino group land with no schema change (2026-07-29): the obvious alternative was a row per hand, which every card-tracking app does. It was never on the table here. One completed night is ONE `matches` row plus one `match_participants` row per player, and PLACEMENT IS DERIVED by ranking net descending — which means a cash night is indistinguishable from any other night to every reader in the app. The crew leaderboard, the rivalry pages, the recap card, the profile aggregates, `feedAgg`, guest linking and the night recap all worked on day one with zero changes to `stats.ts`, and the whole money model rides in `match_participants.meta`, a column that already existed for Mario Party's bonus stars. The temptation to resist, and it will come back with poker: adding a money COLUMN to the ledger. It would be one migration and it would quietly make every casino pack a special case in the highest-traffic file in the repo. Money in meta, placement from net, and the packs stay ordinary.
- The banker's net is derived, so the balance check is checking something else entirely (2026-07-29): stated plainly because the obvious reading of "the table must sum to zero" is wrong. On a player-banked table the banker IS the other side of every hand, so their net is arithmetically the inverse of everyone else's; deriving it means the table sums to zero BY CONSTRUCTION and there is nothing an arithmetic check could ever catch. What the check actually compares is the banker's own count of their rack — which a real banker does at the end of the night anyway — against what the players' numbers say it should be, and the delta is the sum of every typed net. That is a genuinely useful thing to know ("off by $17.25, so a cash-out is too high") and no other pack in this app can check its own correctness at all. Three consequences worth keeping. (1) The check is SKIPPED, not failed, when the banker has not cashed out: an absent count is not a count of zero, and treating it as one would report every table where the players collectively finished up as broken, which is most of them mid-night. (2) It is a WARNING, NOT A VETO — the host is told the exact figure and can still record the night, because the app records what a home game did rather than refereeing it. What it must never do is materialize numbers it already knows disagree WITHOUT saying so, hence 409-then-force rather than either silence or a hard block. (3) The banker's typed cash-out never reaches the ledger; the derived net does. Their own count is the cross-check, not the record.
- The tracker is opt-in and must never be the only way to learn something (2026-07-29): the live tracker defaults OFF for every casino pack and the host can flip it on mid-session. The rule that makes that safe is that the tracker being off cannot lose a stat the cash-out form could have captured, so blackjack's three details (biggest bet, biggest win, blackjacks hit) are BOTH derived from tracked hands AND typed boxes on the cash-out form, prefilled from the tracker when it ran. The subtlety that took a second pass: typed beats derived PER FIELD, not per player. Doing it per player means a host who corrects the biggest bet silently throws away the blackjack count the tracker had been keeping all night, which is a data loss nobody would notice. The related call: turning the tracker OFF keeps the hands already recorded, because they are what those details are derived from and deleting them would lose stats the host had already collected by accident. What is genuinely allowed to be tracker-only is the stuff that cannot be reconstructed after the fact at all — a roulette winning streak, a craps roll length — and those are simply absent on a night the tracker was off, rather than being faked from a total.
- A cash game is not a fixed roster (2026-07-29): every other pack in this app locks its roster at start, because a Smash night has the players it has. A cash table does not work that way — somebody turns up at eleven and sits down, and somebody else busts and leaves — so blackjack has an add-player route and a reopen ("sat back down") route, and a player who never cashed out is treated as still holding chips rather than as a result. That last one is the interesting split: LIVE, an absent cash-out means "unknown", and reporting `-totalIn` would paint a losing night for someone whose chips are on the table. Only at COMPLETION does it become zero, which is the honest reading (you busted and walked), and the End Session confirm names everyone it is about to record that way rather than doing it quietly. Without the split the live TV money board would have shown every player as deeply down until the moment they left, which is precisely backwards.
- One exclusion, at the one place every counter already goes through (2026-07-28, the series-row session): the series summary row is the first row in this ledger that describes rows already in it, and getting the exclusion wrong is invisible — nobody spots that their games-played is one too high per series. The choice was between filtering at each reader and filtering inside `feedAgg`. It went inside feedAgg, because the crew leaderboard was already unified onto that one aggregate precisely so two screens could not disagree about a player, and putting the rule at the shared chokepoint means the NEXT caller inherits it rather than being the one that forgets. What that does not cover is the tallies that never call feedAgg, so those were hunted rather than assumed, and the hunt found one that reading the plan would not have: the RIVALRY MEETING MAP, built in the same loop as feedAgg but after it, which would have counted a series as an extra head-to-head encounter on top of every battle inside it and quietly broken both players' records. The recap rollup was the other: a series row shares its battles' sessionKey ON PURPOSE (that is what makes the deferred-backfill argument work), so it would have landed in their unit and told the room "won 4 of 6 games" about a five-battle series. Both are named in the code next to their `continue`. The regression test that matters most is the negative one: a `bo3` row must still count, because a careless "skip labelled rows" fix would delete Best Of, Mario Party and Grand Prix from everyone's stats just as silently.
- The series row is written by reconciling, and an abandoned series writes nothing (2026-07-28): `over` can flip in three places, and only one of them is the obvious one. The battle that completes the count is obvious; an undo taking it back is easy to remember; the MERCY TOGGLE ending a series with nothing played at all is the one a "write the row when the last battle lands" rule misses, and it would have shipped as "mercy ends the night but nobody is recorded as winning it". So `syncSeriesRow` asks one question — does the ledger agree with `smashdownStatus` right now — and every route that can change the answer calls it. Both halves are idempotent, so it is safe to call twice or on the wrong format. The other call: a series the host ENDS EARLY writes no row. Best Of finalizes an abandoned set to the game leader, and that is right there, because the games inside a set are never materialized and abandoning would lose them entirely. Smashdown is the opposite: every battle is already a row, so an abandoned series loses nothing, and naming a "winner" of a series that did not finish would be inventing a result rather than rescuing one. NO BACKFILL ROUTE was built, which the plan called for, and the honest reason is that there is nothing to backfill: the deferral lasted one session on the same day, so the only sessions that can predate the series row are ones started in the hours between two deploys, and those write their row the moment the host taps End (complete reconciles too). Building a one-shot admin route for zero rows is machinery pretending to be caution. If real history is ever imported, the mechanism already exists: run `syncSeriesRow` over `sessionsForGroup`.
- Smashdown is a FORMAT, and the burn board is DERIVED (2026-07-28): the two calls that shaped the session. (1) It is a fourth entry in `SmashFormat`, not a fifth pack. It shares the roster, the title selector, the character system, the FFA ledger unit, the runtime and the TV route, and the only things it adds are three state fields and a set of rules. Building it as a pack would have meant a registry entry, a route segment, a server file and a ledger key for something that is one `format` string on the rows it already writes — and it would have split Smash's history across two leaderboard tabs, which is exactly what the pack registry's own warning about `gameName` says never to do. (2) The burn board is stored on the session (the TV and the pack page both render it, and it is the centrepiece) but it is only ever WRITTEN by `burnedFrom(games)`. That is what makes undo correct by construction rather than by care: the alternative, subtracting the undone battle's fighters from a maintained set, is right until two battles use the same fighter or a legacy row carries a null, and then the board silently overstates how much of the roster is gone. Recompute, never patch — the same reasoning the KOTH undo has always used for its throne. The related rule: after a battle the picks are cleared so the next one is a fresh choice, EXCEPT on the last battle, where they stay put so every screen can still show what the series finished on and an undo has something to put back.
- Mercy fires on "exceeds", never on "can no longer be caught" (2026-07-28): the natural way to write the clinch check is "no chaser can reach the leader", and in most formats that is the same sentence. It is not the same here, because a tie at the top is a CO-WIN rather than something to break, so a chaser who can still draw level can still change the result. Mercy therefore needs the leader's total to strictly EXCEED every other player's total plus every remaining battle, and the boundary case — leader on 2, chaser on 0, two battles left — must NOT end the series. That case is a named test in both directions, because the failure is invisible: the series just ends a battle early and hands one player a win that was still a shared one. Two smaller calls in the same shape. A clinch is reported even when the mercy toggle is OFF, so the screen can say the lead is unbeatable without acting on it, which is the honest split between a fact and a rule. And the toggle is settable MID-SERIES rather than only at setup: a crew that decides at battle four they have somewhere to be should not have to abandon the night to act on it, and defaulting it off means the surprising behaviour is always the one someone opted into.
- The battle cap is a title property, said out loud before the night starts (2026-07-28): `floor(fighters / players)` looks like a rounding detail and is actually the shape of the format. In Ultimate four players get 21 battles and nobody ever meets the cap; in Smash 64 the same four get THREE. So the cap is computed from the SELECTED title's roster, the number input is clamped to it, and the setup screen states it as a sentence naming the title, the fighter count and the limit, rather than letting the host type 10 and finding out at battle four. A cap of zero (more players than the title can feed, which Smash 64 reaches at nine) is treated as a real answer and blocks the start with the same sentence, not as an error to round up to one. The server clamps independently of the client, and clamps rather than rejects: a client that sends a stale number gets the series that is actually possible instead of a 400 the host cannot act on. The related roster call: Smashdown is capped at 8 players even though the pack's roster allows 16, because everyone plays every battle (that is what makes the cap arithmetic true) and a battle is an FFA game, which `validateFfa` caps at 8. Allowing more would have produced a series that could not be recorded.

Recording this because a half-built feature with no written reason is indistinguishable from an oversight three sessions later.

- The event TV auto-follows instead of being told what to show (2026-07-28): the 07-25 request specified an active-pack POINTER on the event (a nullable column set on start and cleared on end) with the TV subscribing to it, plus a single-active-pack rule to keep the pointer honest. That was dropped in favour of reading what is actually happening: every candidate already carries a status and an updatedAt, so "the most recently touched non-completed session" is derivable with no new state, nothing to set, nothing to forget to clear, and nothing that can disagree with reality. The pointer version has a specific failure this one cannot have: a host who ends a night by closing the tab leaves the pointer set, and the TV then insists on a game nobody is playing until someone clears it by hand. The cost of auto-follow is the opposite failure, following the wrong session when two are genuinely live at once, and that resolves itself the moment anyone touches the one they care about. If the surprise ever actually bites on a real night, an override is a small addition on top; building it first would have been guessing. - The TV waiting screen has two jobs, and the second one is the recap (2026-07-28, James after testing on a real TV): it was built as the pre-game holding screen and it is also what is on between every game, which is the busier of the two states and the one where people actually look at the TV. The order of the players array became load-bearing in the process (the TV reads index 0 as the leader), so the MVP rule is now covered by tests rather than being an implementation detail of one card. - Render the pack's TV view, never navigate to it (2026-07-28): the original spec said the event TV route should redirect (replace nav) to the pack's own TV url. - Beerio needed a completion marker before it could be ranked at all (2026-07-28): the other four packs carry an explicit status that reaches "completed" and drops them out of the running. Beerio had an open signal (the room code on the event) and a completion signal (the /beerio-complete route that writes the standings snapshot) with nothing joining them, so a room stayed "open" forever once opened and would have won the TV for the rest of the crew's history. Three options were on the table: a recency window ("a room older than N hours is dead"), reading the vendored state blob to work out whether the tournament finished, or a stamp. The window is a guess that is wrong at both ends — it kills a long night and resurrects a dead room the next morning — and reading the blob was already rejected once, on 07-27, for the guest-linking work: it is the vendored engine's opaque shape, keyed by a REUSABLE live-session code with no link to a finished match. So: events.beerioCompletedAt, set at completion, cleared when a new room opens, and the room counts as live when the code is set and (there is no stamp OR beerio_sessions.updatedAt is newer than it). The last clause is what makes a second tournament on the same code work with no extra mechanism: the engine writes state, updatedAt passes the stamp, the room is live again. One deliberate extra rule: a code with NO beerio_sessions row never wins, because there is no board to draw and the TV would show a spinner for a room that does not exist. All of this lives in beerio-gn.ts, which is ours; BeerioApp.tsx and beerio.ts stay byte-stable per the 1:1 port rule.
- The tiebreak is declared in code, not left to Postgres (2026-07-28): two candidates genuinely can carry the same millisecond, and without a fixed order the winner depends on row order, which is not stable across queries. That is not a cosmetic problem here. The TV refetches on every relevant broadcast, so an unstable comparator makes the screen flip between two packs on consecutive refetches, and a TV that changes its mind every few seconds reads as broken rather than as a tie. The order is bracket, beerio, smash, mariokart, marioparty, pingpong, asserted in tests both ways round (including with the candidate array reversed, so the test cannot pass by accident of insertion order). Same reasoning for a missing timestamp: it sorts oldest rather than being treated as "unknown, might be newest", so a row with no updatedAt can never win by accident.
- What the bracket updatedAt default does to existing rows, stated here rather than left to be rediscovered (2026-07-28): `ALTER TABLE brackets ADD COLUMN updated_at timestamp NOT NULL DEFAULT now()` stamps EVERY historical bracket with the migration time, so for one moment every bracket the crew has ever played looks freshly touched. It does not matter, and the reason is worth writing down so nobody "fixes" it with a backfill: completed brackets are filtered out of the resolver BEFORE anything is ranked, so a finished tournament's timestamp is never compared against anything, and any bracket that is still live genuinely is the current one. The only observable effect would be on an event with two live things where one is an old un-finished bracket, which is a state that also resolves itself the moment anyone scores anything. - The live pack session is the one screen that must NOT be cached (2026-07-28, cleanup phase 6): the backlog entry for this phase said to build usePackSession on top of the 8a cache helper so the pack pages would inherit the same instant-return behaviour as everything else. That was not done, and the reason is worth keeping. Everywhere else in the app a stale render is cosmetic and corrects itself a moment later. A live pack screen is different in kind, because it is not just showing state, it is offering BUTTONS THAT WRITE: painting a cached roster means a host can tap a player who is no longer in the session, or record a result into a session that has already been replaced, and the write lands before the revalidation arrives to say otherwise. The launch context is excluded for the same reason, since it carries the member list the setup roster is built from and the `live` flag that decides whether the page offers to start at all. The cost is small (you reach these screens once a night and then stay on them) and the alternative is a wrong write, which is the one failure this app cannot take back cleanly.
- Unifying four copies is how the Mario Party gap was found (2026-07-28, cleanup phase 6): Mario Party was the only pack that started its session through the generic call() helper rather than a startSession() of its own, so it silently lacked the 409 confirm-and-replace dance, and the server lacked the matching `!req.body?.force` check that the other three had always had. - A cached identity is a rendering hint, never a permission (2026-07-28, cleanup phase 8a): the app no longer waits for /api/auth/me before it will draw anything, which means for a fraction of a second it can be drawing a screen based on who you were last time rather than who the server says you are. That is safe, and the reason needs to survive in writing so a later session does not "harden" it back into a blocking gate: the cached Me decides what the UI DRAWS, never what the user may DO. Every endpoint authenticates the session cookie itself, server-side, on every request, so a stale cached identity can produce a briefly wrong-looking screen and nothing else. Trading a guaranteed full-screen wait on every launch for a rare half-second of a stale display name is the right way round. The nuance that took a second pass: `undefined` and `null` must stay DIFFERENT states. Collapsing them makes a cold cache render as signed-out, which would flash the login screen at every signed-in user, and since a deploy sweeps the cache by design that would be everyone after every deploy. Flashing a login screen at someone who is signed in is worse than the spinner this phase existed to remove, so an unknown answer still waits and only a KNOWN one paints early.
- Cached content beats a failed refresh (2026-07-28, cleanup phase 8a): wiring the cache in exposed the same latent bug on several pages, which had all been written as `if (error) return <Error/>` BEFORE `if (!data) return <Loading/>`. That ordering is harmless when a page has nothing to show until it fetches, and actively wrong once it does: a revalidation failing (phone lost signal, Render still waking) would throw away a crew page or an event page that was already on screen and perfectly readable, and replace it with an error.
